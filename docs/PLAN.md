## 与原规划的两处差异

1. **历法表没有内联进 `client.js`**，而是放在 Host 侧（`lib/calendar.js`）通过 `/api/todo/month` 提供。
   理由：算法只实现一次；客户端单文件已经很重（约 60 KB），再塞 4 KB 数据和三套算法不划算。
2. **助手对话与待办抽取合并为一个端点** `/api/todo/chat`：模型先做自然语言回复，
   识别到待办时附带 `<todo>…</todo>` 结构化块；服务端流式输出时过滤该块，客户端另做一层兜底。

## 二、路线图

### P2 面板真正能用（进行中）

- 列表视图接真数据：分组（逾期/今天/本周/以后）、勾选、删除、快速添加
- 乐观更新 + 5 秒撤销
- 空态 / 加载态

**验收**：能在页面上记一条待办、勾掉、删掉并撤销，刷新后还在。

### P3 AI 抽取闭环

- 粘贴截图 → canvas 压缩 → `POST /api/todo/upload`
- Host 调 `ctx.llm.stream()`，SSE 推流
- **渐进式草案卡**：解析出一条就渲染一条
- 缺字段标黄 → 人补 → 落库

**验收**：一张会议截图 → 2–3 条带日期和标签的草案；第一张卡 < 1.5s 出现。

### P4 日历视图

- 内联历法表进 `client.js`（单文件硬约束）
- 7×6 网格、上下月补位、农历/节气/节日/生日
- 年月选择器、滚轮翻月、本月回跳

**验收**：任意年份翻月正确；2027 春节落在 2/6；农历生日逐年换算。

### P5 助手人格与记忆

- 单会话 + 滚动摘要 + 每轮注入待办快照
- 人设：时间管理 / 效率建议 / 情绪支持
- 安全边界：不做医疗诊断，遇到严重信号建议求助

**验收**：隔天再聊，它还记得上次说过的事。

### P6 打包发布

- `locale/{en,zh}.json`、`icon.svg`、`docs/DETAIL.md`、README、LICENSE
- 无密钥、无个人数据；`.gitignore` + `files` 白名单
- `git init`，整理成可提交状态

**验收**：干净 clone → 装上即用 → 记录里没有我的私人待办。

## 三、已定的技术决策（不再讨论）

| 问题 | 结论 |
|---|---|
| client → host 通道 | 自建 HTTP 路由（`ctx.webServer.register`，Node 原生 handler） |
| 流式 | SSE（`openSse`，首包实测 204ms） |
| 存储 | `ctx.storageDomain.open(spec)` + 自带 `zod` 依赖；`defineDomain` 不可用 |
| 历法 | 农历查离线表、节气用天文算法；两者都要内联进 `client.js` |
| 图片 | 浏览器 canvas 压缩到 ≤1600px → base64 POST |
| 鉴权 | 同源校验 + `x-dsh-todo` 请求头（路由默认零鉴权） |

## 四、已知风险

1. **鉴权只到「同源 + 自定义头」** —— 本机其它进程仍可直连 `/api/todo/*`。本地应用的固有面，需要写进 README 的已知限制。
2. **`client.js` 会越来越大** —— 单文件硬约束，历法表 4KB + 样式 + 组件都要内联。需要盯住首屏体积。
3. **法定节假日需年度手动同步** —— 缺年份必须显式降级提示，不能静默空白。
4. **官方文档缺失** —— `develop/` 没有 client↔host 章节，本次结论全靠源码 + 实测得出，升级 DSH 后需回归验证。
